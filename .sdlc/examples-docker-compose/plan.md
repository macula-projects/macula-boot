## Risks
- Nacos and Polaris upstream SQL may assume different MySQL modes, users, collations, or initialization order. Keep separate schemas, pin versions, start from empty volumes, and fail health checks visibly if migration/import fails.
- Nacos namespace creation depends on the selected version's management API and authentication defaults. Use an idempotent in-network initializer that waits for health and fails non-zero when namespace setup cannot complete.
- Polaris server configuration and the current Spring Cloud Tencent client may have an undocumented version mismatch. Prove compatibility through registration, discovery, and the gateway echo path; do not mask errors with restart loops.
- A Maven reactor build from the repository root can be slow and can invalidate cache across six image builds. Use BuildKit cache mounts and a parameterized Dockerfile while keeping each resulting runtime image module-specific.
- Health-check tools may not exist in minimal upstream or JRE images. Select checks supported by each pinned image, and install only the minimal runtime tool required in the application image.
- Environment-variable normalization can regress existing Maven/IDE startup, especially the currently inconsistent Alibaba Nacos property paths. Preserve existing defaults and verify both container and host modes.
- Both profiles share MySQL, Redis, network, and project volumes. Use distinct database names and service ports, and verify simultaneous startup to catch hidden name or port collisions.
- Loopback bind syntax and bind-mounted config/SQL files must parse on macOS and Windows Docker Desktop. Avoid host shell scripts, executable-bit requirements, and platform-specific paths or line endings.
- The current machine is macOS ARM64. Image manifests can prove availability but not runtime behavior on Windows or amd64; those remain explicit Stage 4 platform gaps unless another environment is provided.
- Local example credentials and upstream sample tokens are security-sensitive if exposed beyond localhost. Bind host ports to loopback, document their scope, and never treat them as production defaults.
- Rollback is source-level reversion of these files. Named volumes survive normal `down`; users must explicitly run the documented `down -v` reset when reverting across incompatible schema changes.

## Deviations
- Retained the complete upstream Polaris v1.18.1 server configuration instead of reducing it. Runtime startup depends on upstream listener, plugin, cache, and maintenance sections that cannot be safely removed without broader Polaris-specific validation. The Compose file still limits the local use case and publishes only the documented loopback ports, so verification scope is unchanged.
- Added writable `/app/polaris/backup` and `/app/polaris/logs` directories to the shared application runtime image. The Tencent client creates these relative paths during startup; creating and owning them in the image is required to keep the planned non-root runtime user. Image-content and runtime-user checks cover the additional directories.
- Added container-only Redis connection variables and pointed the Tencent client's Nacos-compatibility address at Polaris port 8848. Runtime startup exposed these implicit framework dependencies; the variables are confined to Compose and do not alter Maven/IDE defaults. Full-stack and dual-profile smoke checks cover the change.
- Added Tencent consumer and gateway demo-path allowlists through service-specific Compose environment variables. Their health checks and required anonymous gateway echo otherwise returned HTTP 401. Keeping the allowlists out of the checked-in application defaults preserves existing host-run security behavior; the Tencent gateway smoke check proves the container-only override.
- Added loopback host ports `18849`/`19849` for Polaris's Nacos-compatible HTTP/gRPC API and made `18849` the Tencent applications' overridable host default. Stage 4 host-run verification showed that Spring Cloud Tencent initializes this compatibility layer even when Polaris discovery/config use ports 8091/8093; without the address and its derived `+1000` gRPC port, a host-started provider fails before the web server starts. The extra ports avoid Alibaba Nacos 8848/9848 collisions and are covered by Compose rendering, Middleware-only reachability, and host-run startup checks.
- On 2026-09-20, the originator explicitly waived the remaining Windows Docker Desktop, native `linux/amd64`, and Alibaba host-default runtime checks after reviewing the available evidence. Those environments are not claimed as executed: cross-architecture support is evidenced by manifests, runtime smoke tests were performed on macOS ARM64, and Alibaba container/default-value behavior was covered without stopping the unrelated process occupying host port 8848.
- Stage 5 review found that direct `sed` substitution treated overridable MySQL passwords as replacement syntax. The Polaris startup command now escapes backslash, `&`, and the delimiter before rendering its runtime config, and the proof includes an isolated clean-volume smoke test using all three characters. The host-run documentation also now explains that `.env` port overrides must be mirrored into Maven/IDE environment variables and that Nacos-compatible gRPC ports remain HTTP `+1000`.
