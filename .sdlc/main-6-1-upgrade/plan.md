## Risks
- Creating `6.0.x` at the wrong commit would contaminate the maintenance line. The operation is ordered first and guarded by exact local and remote SHA checks; no force push is planned.
- Boot `4.0.8` is newer than the `4.0.2` version recorded in the Cloud `2025.1.1` BOM metadata. Maven convergence, focused tests, and full Stage 4 verification must demonstrate compatibility; any need to change the accepted platform versions returns to the reviewer.
- Boot 4, Framework 7, Jackson 3, and Gateway 5 can change Java types, auto-configuration behavior, serialization, and reactive APIs. Changes stay within compiler- or test-proven compatibility scope, and user-visible differences require migration notes and regression tests.
- Alibaba 2025.1 removes the old bootstrap configuration path. An incomplete move to Config Data imports can make applications start without remote configuration or use the wrong namespace. Runtime smoke checks must prove configuration is loaded from the intended source.
- Other managed libraries may not yet support Boot 4 or Jackson 3. Compatible upgrades can be proposed only when needed for the accepted migration; removing a feature, downgrading the accepted platform, or making an unrelated dependency sweep invalidates the plan and requires human direction.
- Existing downstream users may depend on Boot 3-era public types or serialized output. Preserve APIs and wire behavior where upstream permits; document unavoidable source or behavior changes as 6.1 migration requirements.
- Docker and external Nacos, Polaris, Redis, databases, or cloud services may be unavailable locally. Environment failures are reported separately and cannot be converted into a healthy result.
- Pushing the new branch does not guarantee GitHub protection rules cover it. Branch-protection configuration remains a separate repository-administration concern.
- Rollback keeps `6.0.x` fixed at the pre-upgrade commit and reverts discrete 6.1 commits on `main`; it does not use `release.sh`, destructive resets, tags, or production deployment.

## Deviations
- The first Boot 4 Maven model load proved that several accepted Boot 3/Cloud 4 starter coordinates are no longer managed. The implementation file set therefore expands to the RocketMQ, idempotent, security, Seata, Spring Retry, operation-log, web, and gateway POMs plus their dependency documentation. `spring-boot-starter-aop` moves to the supported `spring-boot-starter-aspectj`; the Gateway starter moves to `spring-cloud-starter-gateway-server-webflux`. Boot 4.0.8 publishes no Undertow starter, so the web Starter must return to Boot's supported default Tomcat runtime and document that 6.1 migration. This is compiler- and repository-metadata-driven, changes runtime-server behavior only where upstream removed the old integration, and adds focused web/gateway proof.
- `AGENTS.md` (and therefore the `CLAUDE.md` symlink view) must change from the stale Boot 3.5 project description to Boot 4.0 after the migration. This protected-instruction change was not listed originally; it does not alter workflow policy, but Stage 4 must explicitly inspect the diff and record that no skill or hook changed.
- Spring Cloud Gateway 5 moved its built-in configuration hierarchy under `spring.cloud.gateway.server.webflux`. In addition to the planned example and archetype migration, the gateway Starter's CORS-presence condition must inspect the new prefix or it silently skips user CORS configuration. This compiler-independent upstream contract change expands the source file set to `ResourceServerConfiguration.java` and requires focused gateway condition coverage.
- The first clean reactor compile failed in the Security Starter because Boot 4 modularized OAuth2 Resource Server auto-configuration and moved `OAuth2ResourceServerProperties` plus its decoder condition annotations to `org.springframework.boot.security.oauth2.server.resource.autoconfigure`. The compatibility scope therefore includes the Security and Gateway `ResourceServerConfiguration.java` imports; behavior and public configuration keys remain unchanged, and focused security/gateway context tests must cover the new classpath.
- Continuing the reactor compile failed in the JPA Starter because Boot 4 split JPA auto-configuration into dedicated modules, renamed `JpaRepositoriesAutoConfiguration` to `DataJpaRepositoriesAutoConfiguration`, and moved Hibernate/JPA customizer packages. `JpaAutoConfiguration.java` therefore adopts those Boot 4 types while preserving its ordering and bean conditions; focused JPA auto-configuration tests remain part of proof.
- Framework 7 removed `HttpHeaders`' direct `Map` surface in favor of `containsHeader` and `headerSet`, and Spring Security 7 replaced `ReactiveAuthorizationManager.check` with `authorize` returning `AuthorizationResult`. Clean compilation therefore expands the compatibility changes to web `ControllerResponseAdvice` plus gateway `GrayscalePublishGlobalFilter`, `RmOpaqueTokenEndpointFilter`, and `ResourceServerAuthorizationManager`; the logic remains equivalent and existing/focused response, filter, and authorization tests must verify it.
- Boot 4 moved the Netty reactive server factory into its dedicated Reactor Netty module/package. The Alibaba gateway example's `GatewayConfig.java` import therefore changes to `org.springframework.boot.reactor.netty.NettyReactiveWebServerFactory`; its dual HTTP/HTTPS port behavior is unchanged and must be covered by example compilation/runtime smoke proof.
- A clean test build (unlike the earlier incremental compile) proved that Boot 4 renamed and moved Redis auto-configuration to `DataRedisAutoConfiguration` and `DataRedisProperties`. The Redis Starter's `RedissonAutoConfiguration.java` and `RedissonConfigBuilder.java` therefore use those types while retaining the `spring.data.redis` contract and Redisson construction behavior; Redis configuration tests are added to focused proof.
- The same clean test build proved that Boot 4 modularized cache auto-configuration and metrics, moving `CacheAutoConfiguration`, `CacheProperties`, and `CacheMeterBinderProvider`, while the Cache Starter also ordered itself after the removed Redis type. `TwoLevelCacheManager`, `TwoLevelCacheAutoConfiguration`, and `TwoLevelCacheMeterAutoConfiguration` therefore adopt the Boot 4 cache packages and `DataRedisAutoConfiguration`; cache semantics and configuration keys remain unchanged, and cache context/metrics tests are added to focused proof.
- Boot 4 also moved `JacksonAutoConfiguration` into its dedicated Jackson module. The existing `WebAutoConfigurationTest` must import the new package so its application-context assertions execute on Boot 4 rather than failing during test class loading; the test scenarios and production behavior are unchanged.
- Boot 4's security modularization removed `SecurityProperties` from the Web Starter's transitive classpath. The web test fixture `DemoDto` used its nested `User` merely as an arbitrary JSON field, so that field becomes `Object` rather than adding an unrelated Security dependency; the `user` property is preserved and production API is unaffected.
- A focused web context test then exposed the complete Boot 3/Jackson 2 conversion path left in incremental output. Boot 4 uses Jackson 3's `JsonMapperBuilderCustomizer`, integrated Java Time support, `tools.jackson` serializers/deserializers, and Framework 7's `AbstractJacksonHttpMessageConverter`. The Web Starter's configuration, advice, converter, number/null/sensitive serializers, annotation binding, MVC configurer, and tests therefore move to Jackson 3 while retaining historical converter class names and wire behavior; focused serialization and context tests must prove compatibility.
- Boot 4 modularized MVC test auto-configuration, so the Audit Log integration test no longer receives `AutoConfigureMockMvc` from the general test starter. The Audit Log POM adds test-scoped `spring-boot-webmvc-test`, and `AuditLogAspectIT` uses the new `org.springframework.boot.webmvc.test.autoconfigure` package; production dependencies and behavior are unchanged.
- Boot 4 moved Micrometer metrics auto-configuration into a dedicated module/package. `PrometheusAutoConfiguration` and its focused test therefore import `MeterRegistryCustomizer` from `org.springframework.boot.micrometer.metrics.autoconfigure`; its application common-tag behavior is unchanged and the existing test supplies the proof.
- Boot 4 moved `WebServerApplicationContext` into the dedicated `spring-boot-web-server` module/package, which is no longer transitively present through the old monolith. The Alibaba Starter adds that focused Boot module, and its delayed Nacos registration auto-configuration, listener, and test use `org.springframework.boot.web.server.context.WebServerApplicationContext`; delayed registration behavior is unchanged.
- Boot 4 moved Kafka auto-configuration into the dedicated `spring-boot-kafka` module and `org.springframework.boot.kafka.autoconfigure` package. The Kafka Starter adds that focused Boot module and its compatibility test imports the relocated `KafkaAutoConfiguration`; the existing Kafka producer/template contract remains unchanged and the focused context test supplies proof without requiring a broker connection.
- Spring Security 7 removed the legacy WebSocket broker configurer and metadata registry. `WebSocketSecurityConfiguration` therefore enables the supported WebSocket security infrastructure, publishes an `AuthorizationManager<Message<?>>` built from `MessageMatcherDelegatingAuthorizationManager.Builder`, and preserves the prior disabled same-origin/CSRF-channel behavior with the documented interceptor override; `MessageSecurityMetaSourceCustomizer` adopts the new builder type while retaining the same rule-ordering extension point. Focused WebSocket authorization/context proof is required because this is a public source-compatibility change forced by the upstream removal.
- The Operation Log Starter exposes and manipulates Jackson tree nodes directly, so Boot 4's Jackson 3 baseline requires its DTO, listener, utility, and adjacent tests to use `tools.jackson` types. Jackson 3 renamed `TextNode` to `StringNode` and favors immutable mapper construction; the truncation, fallback, and self-reference behavior remains unchanged and existing utility tests provide focused proof.
- Dependency-tree inspection after the reactor passed showed that Commons still exported Jackson 2 databind and the JPA/MyBatis base-entity serializers still used Jackson 2-only databind annotations, which Jackson 3 would ignore. Commons therefore moves its databind dependency and JSON contract test to Jackson 3, and both entity types adopt Jackson 3 `JsonSerialize`/`ToStringSerializer`; the `com.fasterxml.jackson.annotation` package remains valid because Jackson 3 intentionally retains the 2.x annotations artifact. RocketMQ alone retains Jackson 2 because RocketMQ Spring 2.3.4 constructs Framework's legacy `MappingJackson2MessageConverter` and brings Jackson 2 itself; its Java-time customization is an isolated third-party compatibility path rather than the application HTTP mapper.
- Real archetype generation proved that the newly added Spring environment placeholders with colon defaults are parsed as invalid Velocity expressions. The six filtered `application.yml` templates therefore escape only those four runtime Nacos placeholders so generated projects receive the intended literal `${NACOS_*:default}` values; successful generation plus generated-parent validation supplies proof.
- Compiling the generated project then exposed a Boot 3 `RedisProperties` import hidden in the archetype-only gateway Java template. That configuration moves to Boot 4's `DataRedisProperties`, matching the earlier Redis Starter migration and preserving both default and system Redis client construction; regenerated-project compilation is the required proof because repository compilation does not compile template Java sources.
- The Redis and Gateway README multi-client examples referenced the same removed `RedisProperties` API even though their behavior remains supported. They are synchronized to `DataRedisProperties`, and a stale Jackson 2 date-format class comment is removed from the Web test resource so maintained examples do not direct users to removed Boot 3 types.
