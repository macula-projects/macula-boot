# Spec: 风险处置与认证因素配置（现有设计增量，修订2）

> 菜单最新修正（2026-11-21）：通用安全、密码策略独立；多因素认证菜单下使用“MFA策略”“多因素认证配置”两个Tab。密码策略按用户区分，具体增量见security-settings-structure.md。


> 当前范围（2026-11-21）：接入应用暂不增加MFA配置；平台管理因素，统一风险/账号/敏感场景决定认证要求。文末最新用户修正优先于此前应用级MFA扩展建议。

Status: accepted

## Source intent
现有accepted intent.md及用户本轮明确修正：“不用保留旧配置。多因素认证只是配置比如另外的因素启用规则，以及具体的因素配置，比如短信、邮件、PassKey等”。本修订覆盖此前旧配置兼容/映射与MFA承担强制触发策略的约定；实施计划仍待批准，不自行批准源码或运行切换。

## Requirements
1. 风险评估统一识别设备、IP、UA、地域和失败记录，输出等级、原因及环境摘要。风险/场景策略决定LOW/MEDIUM/HIGH采取ALLOW、REQUIRE_AUTH或BLOCK，以及所需认证强度、证据年龄和是否需要针对变化后的环境重验。
2. MFA只管理认证因素的启用规则与具体配置。启用规则包括因素开关、适用主认证方式/场景/用户范围、已绑定要求及可用组合；这些规则回答“可以用什么来补验”，不再回答“何时必须追加认证”。
3. MFA页面分别呈现短信、邮件、TOTP验证器动态口令、Passkey配置：短信/邮件的验证参数、消息渠道与模板关联、配置/绑定/投递可用状态；Passkey的UV要求及可信RP/Origin配置状态、注册和管理能力。短信/邮件复用现有消息供应商、受保护秘密和投递服务，不复制AK/SK/邮箱秘密；相关编辑仍执行各自原权限。认证因素与消息Channel保持不同模型。
4. 删除旧MFA的RISK/OFF/ALWAYS触发模式、adaptiveEnabled、reauthOnEnvironmentChange等退役配置与执行分支，不保留LegacyAuthenticationPolicyAdapter、旧源选择、双读、旧新映射或失败回退。新风险/因素配置为唯一权威，缺失或损坏明确拒绝，不通过旧值恢复。
5. 风险处置、账号/敏感接口的强认证要求共同决定最终要求；BLOCK与账号禁用/管理员锁定优先。因素选择只取已启用、适用、已绑定、配置完整且实际可用的独立组合。PASSWORD+绑定OTP可按要求使用；重复同类OTP和SMS+EMAIL不冒充独立MFA；UV Passkey由官方服务器验证UV，不接受客户端通过标志。无合格因素时拒绝并提供受控恢复指引。
6. 登录、MFA续接、刷新及敏感访问复用同一风险处置决策和策略上下文；同一情境完成补验后可复用，访问/刷新不延长完成时间，不每请求重置验证起点。旧策略验证结果不能在配置变化后重标为新策略证据。
7. 保持平台因素配置/风险处置与租户评分/消息基础配置的权限边界；用户账号、密码哈希、真实应用及外部身份绑定、已绑定因素、消息供应商凭据和审计不因移除旧配置被清除。旧配置清理只针对退役的风险/MFA合同，不扩大到设备、密码、会话或其他配置。

## Non-goals
不新增任意规则脚本、后台监控线程、永久风险锁号或独立恢复协议。不创建第二套短信/邮件投递或验证码预算；不改变业务授权、原Bearer合同、可信RP来源。不以“删除旧配置”推断真实库删除、迁移、策略启用、容器切换或远端交付授权。

## Design
风险评估 → 风险/场景处置 → 认证要求 → MFA选择合格因素并执行 → 证据记录及成果发布。企业/场景的必须认证要求放在风险/场景策略，账号个人安全要求留在账号安全配置，不在MFA再放一套强制触发开关。

MFA页面含“因素启用与组合规则”“短信”“邮件”“验证器动态口令”“Passkey”；风险页面含评分、等级处置、范围、强度/时限及环境变化处置。现有消息渠道作为因素的投递依赖，只保留一份真实供应商配置和秘密。尚未完成的Passkey必须显示未就绪，不能仅因配置开关打开就宣称可用。

## Data and interfaces
新策略采用风险/因素分区、不可变版本、草稿/有效指针、CAS及owner绑定的短期预览；预览绑定当前新策略有效版本/摘要，不再绑定任何legacy源。只提供新合同，退役旧MFA读写接口与字段；历史迁移脚本不重写，新增迁移清理退役策略存储，但真实环境清理另行授权。

切换前检查新配置、实际可用因素和操作者可登录路线；只按新规则预检，不要求保持旧行为。新旧应用不得混跑旧/新配置合同；缺少可用因素或新配置时停止切换，不静默生成宽松规则。

## Flagged concerns
- [non-blocking] 用户已明确取消旧配置保留；部署需按新策略准备完整配置并重新验证，不承诺旧API/旧策略兼容。原已构建四个镜像不含本修订。
- [non-blocking] Passkey及供应商管理仍在主任务实施中，本增量不得伪造这些能力就绪；启用依赖不可用因素的强制策略必须拒绝。
- [non-blocking] 真实库仍为V34，V35–V37及后续迁移、策略启用和容器切换尚未授权；本设计确认不代替这些授权。

## Verification strategy
验证三档处置、因素开关/主认证方式适用/绑定/配置/组合矩阵、SMS/邮件共享投递与预算只计一次、UV拒绝及缺因素恢复。搜索并证明运行路径不读旧mode/adaptive字段或legacy源；旧API拒绝而非悄悄保存。覆盖新配置缺失/损坏拒绝、越权、CAS/预览重放、策略切换竞争、同情境补验后复用及主认证成果发布回归；旧账号/真实凭据/绑定/审计不被清理。

政策依据：两仓AGENTS.md及现有模块规则、REVIEW.md。未引入额外组织合规要求。该状态表示用户已明确指示的设计修正，不表示实施计划已获批、代码/测试完成或运行环境切换。


用户最新因素范围：EMAIL、SMS、TOTP、PASSKEY。TOTP及Apple/Windows/Android的用户自助WebAuthn范围、登记/撤销/恢复与核验证据约束见[totp-webauthn-scope.md](totp-webauthn-scope.md)，此前三因素描述据此修正。


## 用户选择与后台风险规则（用户后续明确要求）

用户要求“MFA方式用户应该可以选择”，并补充“后台启用使用哪几种，什么风险等级要哪种”。两者组合为后台约束、用户在合格集合内选择，不做二选一的产品限制。

1. 平台因素配置决定EMAIL/SMS/TOTP/PASSKEY哪些可启用，以及适用主认证方式/场景/目录与独立组合规则。管理员停用因素不删除用户已有绑定或秘密，但停用后不能用于新的认证成果。
2. 风险/场景处置在LOW/MEDIUM/HIGH各档配置动作、allowedFactors、minimumStrength和证据时限；可要求某一种、允许几种供选择，或BLOCK拒绝本次操作。指定PASSKEY时仍验证UV，不能只以方式名当强度证明。配置不自动激活或改写真实环境。
3. 本次可选集合=平台启用且适用的因素∩该风险/场景允许因素∩用户已绑定有效因素∩当前实际可用因素，再筛除不满足主认证独立性、UV或最低强度的组合。空列表不表示全部，无可选因素时明确拒绝/引导既有受控恢复，不自动放宽。
4. 挑战接口只返回该owner本次真正可选的方式；多种时提供选择/切换，只有一种时直接展示该方式。用户不能选择策略禁用的方式，也不能用自报factor、绑定信息或前端选项跳过后端复核。
5. EMAIL/SMS显示发送验证码，TOTP显示动态码输入且没有发送按钮，PASSKEY调用浏览器认证器。切换仍绑定原owner、应用、challenge、策略版本和总体尝试预算，不重建挑战扩充次数，不自动重放原业务写请求。
6. 风险allowedFactors及minimumStrength纳入不可变PolicyEvaluationContext、挑战和有效策略摘要；保存/激活预检计算风险等级对应的真实可用集合与操作者自锁风险，不能只统计账号拥有任意一个因素。
7. 测试覆盖：多方式自主选择/切换、单方式限定、平台禁用、风险限定、未绑定、设施/浏览器不支持、强度不足、交集为空、跨owner/旧策略拒绝；证明前端可选项与后端实际允许结果一致。该补充是用户直接明确的需求，具体实现计划仍待补审与批准。

示例仅说明可配置能力，不是已启用默认值：低风险不追加认证；中风险允许密码主认证后的EMAIL/SMS/TOTP或满足要求的UV Passkey；高风险限定UV Passkey，或由管理员配置BLOCK。账号硬拒绝、个人/接口必须认证及业务权限约束仍独立。


最终确认记录：用户“OK，确认”接受UV Passkey在符合当前策略时直接满足MFA/强认证；具体边界见totp-webauthn-scope.md最后一节。四因素、后台分级限制与用户合格集合内选择的要求已合并进risk-response-plan.md，新增范围仍待独立计划审查与工程师实施批准。


## 历史修正：平台因素能力与应用级MFA要求（2026-11-20，已被下文2026-11-21决定取代）

用户明确：“后台主要是配置可用的MFA方式。IAM接入应用那里配置对应的启用那种MFA方式，是否强制启用还是根据风险自适应启用。”本条是需求职责的最新修正，优先于此前把企业通用强制触发范围放在平台风险分区的约定；不是恢复旧MFA JSON或旧全局OFF/RISK/ALWAYS合同。

1. 平台MFA管理提供EMAIL、SMS、TOTP、PASSKEY的全平台可用开关、因素参数及设施就绪状态；消息供应商/模板及秘密继续沿用唯一现有管理来源。这里不再配置某应用是否强制或自适应要求MFA。
2. IAM接入应用配置本应用允许的MFA因素（平台已启用集合的子集），并选择“强制认证”或“风险自适应”。主登录方式与MFA因素是不同字段：例如PASSWORD主登录加TOTP补验，不把SMS主登录再次验证SMS算作独立MFA。
3. 强制认证在允许继续的用户登录中始终要求满足本应用的MFA强度；已具备本应用允许且满足强度/时限/环境的服务器证据可直接满足，真实UV Passkey主登录也可满足，不机械地重复挑战。账号硬拒绝和风险BLOCK仍优先。
4. 风险自适应使用风险规则对LOW/MEDIUM/HIGH的处置结果决定是否补验；风险判断不在MFA页面复制一套。平台风险分区的通用强制触发范围（例如requiredLoginUserTypes）须按本修正重新归属到应用要求，避免与应用模式重复。
5. 用户可选集合=平台启用且适用 ∩ 本应用允许 ∩ 本次风险/敏感场景允许 ∩ 本人已绑定有效 ∩ 实际可用 ∩ 独立性/UV/最低强度要求。用户在该集合内选择或切换；需要MFA而集合为空时明确拒绝/进入既有受控恢复，不跨应用借用允许集合或自动放宽。
6. 应用限制必须进入服务器原PolicyEvaluationContext及版本围栏：创建挑战时捕获可信应用ID、应用授权/认证配置版本与有效MFA要求，后续核验/证据/发布复核同一原应用版本；应用配置变化使旧挑战失效，不能只检查平台有效版本。预览与能力预检亦须按实际应用路线及该应用MFA要求计算。
7. 个人强安全设置、因素管理近期强认证和受保护敏感接口的明确要求继续收紧准入；应用自适应不能关闭这些要求。机器凭据不进入交互式用户MFA挑战。

本次仅同步用户已明确的产品职责修正。接入应用的数据模型、表单/API、授权版本联动、应用围栏及预检/页面测试文件清单须并入修订实施计划；此前计划的应用归属不足部分不视为已批准的新源码清单。本记录不自批新设计/实施门禁，业务源码未因本条修改，真实迁移/配置启用/镜像切换仍未执行。


## 当前范围修正：暂不提供接入应用MFA配置（2026-11-21）

用户明确：“OK，IAM接入应用暂时不要MFA配置了。”此前应用级MFA修正中有关应用允许因素、强制/自适应模式及其新增数据/API/表单/版本的要求暂不实施，不作为本轮源码任务。

1. 平台MFA后台管理EMAIL、SMS、TOTP、PASSKEY的可用方式、适用规则、具体因素参数及真实设施状态。
2. 是否要求补验仍由统一风险/场景处置、账号个人强安全要求及敏感操作要求决定；MFA页面不另放重复的风险触发开关。
3. IAM接入应用本轮不增加MFA方式选择、MFA强制/自适应模式、对应字段/API/表单/迁移或预览激活流程，也不恢复旧全局MFA JSON模式。
4. 用户在平台与本次风险/场景允许、本人已绑定且实际可用的独立因素集合中选择；个人中心继续参考用户提供的卡片和登记向导设计。需要补验而集合为空时不放宽要求。
5. 原有可信client、应用授权版本及owner/设备/认证会话绑定继续有效；“暂不增加应用MFA配置”不代表删除既有应用隔离或放宽证据的跨应用复用边界。

本条仅记录用户直接给出的范围收缩，取代前一节应用级MFA扩展建议；不自批实施/测试门禁，不修改业务源码、真实配置或部署环境。


## 最新菜单与密码策略需求（2026-11-21）

用户明确通用安全与密码策略拆为独立菜单，密码策略允许按不同用户区分；原风控分级界面命名为“MFA策略”，与“多因素认证配置”置于“多因素认证”同一菜单的两个Tab。此需求取代此前风险/因素分属两个菜单以及密码表单仍位于通用安全页的安排，IAM接入应用仍不增加MFA配置。
